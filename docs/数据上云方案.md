# 衣物 / 搭配 / 日历 数据上云方案（存 MySQL）

> 2026-09 二期第二步。第一步（照片上 OSS）已完成并实测通过。
> 现状：所有数据都在小程序本机 `wx.storage` 里，换手机/清缓存就没了。

## 0. 现在本机到底存了什么（改造对象）

| 存储键 | 内容 | 上云 |
|---|---|---|
| `clothes_items` | 衣物数组 | ✅ |
| `clothes_outfits` | 搭配数组（含 9 格位置表、封面、草稿标记） | ✅ |
| `clothes_wear` | 日历：`{'2026-09-20': '搭配id'}` | ✅ |
| `clothes_pending_items` | 编辑搭配时「挑了还没点完成」的临时状态 | ❌ 纯前端临时态，取一次就清 |
| `clothes_seeded` | 「演示数据已填过」标记 | ❌ 前端标记 |

数据形状（沿用，不重构）：

```
衣物 { id:'i<ts>', name, category, sub, colors[], seasons[], occasions[], image(本机路径), imageUrl(OSS), createdAt }
搭配 { id:'o<ts>', name, nameAuto, occasions[], itemIds[], slots[9], photo(本机封面), photoFor, draft, createdAt }
```

**id 建议直接沿用本机那套字符串 id**（`i1789...` / `o1789...`）当云端主键 —— 两套 id 互相映射是这类改造最容易出事的地方，没必要。

## 1. 云端表设计（3 张表，新增表、不动老表）

```
clothes_items
  id            varchar(32)   复合主键的一部分（本机 id 原样搬来）
  user_id       bigint        复合主键的一部分
  name          varchar(64)
  category      varchar(16)   上装/下装/外套/裙装/套装/鞋/袜帽/配饰（2026-09 加「套装/袜帽」；
                              后端**不校验白名单**，是自由字符串；帽子/围巾从「配饰」挪到「袜帽」后，
                              老记录仍写着 acc+hat —— 前端按二级归属（mock.catOfSub）归到新一级，数据不迁移）
  sub           varchar(24)   二级细分，可空
  colors        json          色 key 数组
  seasons       json
  occasions     json
  image_url     varchar(255)  OSS 地址（本机 image 路径不上云，跨设备无意义）
  created_at / updated_at / deleted_at(nullable)
  唯一键 (user_id, id)

clothes_outfits
  id, user_id, name, name_auto(bool), occasions(json),
  item_ids  json, slots json,          -- slots = 9 格位置表（衣物 id / null）
  cover_url varchar(255),              -- 搭配封面（canvas 出图 → 也传 OSS）
  created_at / updated_at / deleted_at
  唯一键 (user_id, id)

clothes_wear_logs
  user_id, date(date), outfit_id varchar(32), created_at
  唯一键 (user_id, date)               -- 一天只记一套，符合现在的口径
```

**为什么 garment 用 JSON 列而不是关联表**：颜色/季节/场合就是一组 key，只做整体读写、没有「按颜色统计」这类需求；多三张关联表只会让同步逻辑变复杂。衣物与搭配的关系（`itemIds`）同理存 JSON，只有「这件衣服被哪些搭配引用」一个查询，前端本地算又快又省事。

## 2. 接口（都在 `auth:sanctum` 组内，前缀 `/api`）

```
GET    /api/clothes/sync             一次拉全量 {items, outfits, wears}（进页面/登录后一次）
POST   /api/clothes/sync             批量推（待推的条目+待删的条目），一条事务搞定

POST   /api/clothes/items            新增/更新（upsert，按 (user_id,id)）
DELETE /api/clothes/items/{id}       删除（连带删 OSS 图）
POST   /api/clothes/outfits          新增/更新
DELETE /api/clothes/outfits/{id}     删除（连带删封面）
PUT    /api/clothes/wears/{date}     记某天（body: outfitId）／传空串 = 清除
GET    /api/clothes/wears?month=2026-09   日历按月拉（可选，全量 sync 里也能带）
```

推送用「批量 + 队列」而不是「每次改动打一个接口」：弱网下一次请求把攒的改动都推上去，跟照片补传（`img-sync.js`）一个套路，失败就留着下次再推。

**统一响应**沿用现有 `{code, msg, data}`；错误一律 JSON（`ForceJsonResponse` 中间件已就位）。
**删除用软删**（`deleted_at`）而不是硬删：多端不会「删除被同步回来」，OSS 对象仍按 key 真删。

## 3. 小程序侧怎么改（关键决策）

### 推荐：本机 storage 当缓存，后台同步（页面几乎不用改）

`store.js` 的**函数签名全部不变**（`getItems()` 还是同步返回数组，只是读本机缓存），新增 `utils/cloud.js`：

```
拉：各页 onShow / 登录后 → cloud.pull()     拉云端全量 → 合并进本机缓存 → 页面 refresh()
写：store.saveItem() 之后 → cloud.push()     先写本机（立刻有反馈），再推接口
     失败 → 记进「待推队列」(dirty)，下次进页面自动补推
合并：按 id；同 id 两边都有 → 比 updated_at 取新的（冲突以云端为准）
```

页面改动量：7 个页面各加一处触发（跟现在 `imgSync.sync()` 的接法一模一样），`store.js` 内部加一层合并逻辑。**不动 44 处调用点**。

### 备选：全异步改造
`store.js` 全改 async，页面加 loading 态 —— 44 个调用点 + 每个页面的加载/空态都要重过一遍，工作量大概是前者的 3 倍，收益只是「数据永远是刚拉的」。不建议现在做。

## 4. 首次登录（最容易出事的一步）

本机已经有一堆数据，云端可能是空的，也可能有（换手机/重装）：

| 情况 | 处理 |
|---|---|
| 云端为空、本机有数据 | 把本机全量推上去（现有数据当初始数据） |
| 云端有、本机也有 | **按 id 智能合并**：只在一侧的补齐；两侧都有的比 `updated_at`（云端优先） |
| 本机为空、云端有 | 直接拉下来 |

不建议「本机覆盖云端」或「云端覆盖本机」：用户没法预期，一撞就丢数据。

## 5. 顺带要做的两件事

1. **搭配封面也要上云**：现在封面（`photo`）只是本机 canvas 出的图，没上传 → 换手机搭配列表全是空图。改法：出图后传 OSS（`dir=outfit` 白名单已就位）→ 存 `cover_url`；显示仍「本机优先」。
2. **删除时连带删 OSS 对象**：现在删衣物/搭配只删本地记录，云端图会变垃圾。后端在 delete 里按 URL 反查 key 删掉（`ImageStorage::deleteByUrl` 已有）。

## 6. 部署顺序 & 回滚（线上线下隔离）

1. 后端先发：3 张新表 migration + 新接口 —— **只加表、不动老表**，老版本小程序压根不调这些接口，线上零影响
2. 小程序后发：新版启动即 sync；用户升级后第一次打开把本机数据合并上去
3. 回滚：旧版小程序照旧读写本机 storage，云端数据仍在（不丢）；后端接口留着不碍事

## 8. 风险 / 要提前想清楚的

1. **演示数据会一起上云**：本机现在那 12 件 `m01–m12` 种子衣物 + 十几套回归脚本残留的未命名搭配，会被当成「用户数据」推上去 → 建议上云前先清干净（保留你真正录的）。
2. **双端同时用**（开发者工具 + 真机）：同一条记录两边改，后推的赢（last-write-wins）。单用户场景可接受；要更稳就加 `rev` 版本号，冲突时提示用户选。
3. **断网**：本机缓存兜底，能看能改；改动排队等联网补推。
4. **删除衣物后搭配里的悬空引用**：与现在行为保持一致（卡片上显示「已删除」），云端不做级联清理。
5. **日历**只存搭配 id（现在的口径），搭配被删后那天显示「这套已删除」—— 上云后行为不变。

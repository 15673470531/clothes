# 穿搭照识别（2026-10）

> 拍一张全身穿搭照 → AI 认出身上有哪些衣物 → 用户**逐件确认** → 一次性加入衣橱。
> 目的是省掉「一件件拍衣物 + 一件件填属性」。
>
> 口径（2026-10 用户拍板，编号是当时方案里的选项）：入口放「＋」弹层**第一项**、模型**可配置**
> （默认 `qwen-vl-plus`）、每件衣物**默认用裁剪图**（可切整张）、AI 只猜**品类/细分/颜色/名称**、
> 每人每天**5 次**、认出来的衣物**默认不自动洗白底**、一次最多认 **8 件**。

## 一、链路

```
小程序 → chooseMedia 一张图 → 压一道 → POST /api/items/recognize (multipart)
        ↓ 后端 ScanService
        ① 原图存 OSS（百炼只吃公网 https 直链）→ sourceUrl
        ② qwen-vl 识别 → 只吐 JSON（品类/细分/颜色/名称/框）
        ③ 收敛到小程序那套常量表（对不上的品类整件丢掉）
        ④ GD 按框裁出每件的图 → 存 OSS → 当这件衣物的照片
        ↓ 返回 { sourceUrl, count, truncated, leftToday, items[] }
小程序 → storage 存结果 → pages/scan-confirm 逐件确认
        ↓ 点「加入衣橱」（N 件）
        cloud.saveItems → POST /api/clothes/sync → 真的建衣物 + 结算衣架
```

**两条铁律**：识别阶段**不落库、不扣衣架**（用户点了「加入衣橱」才建衣物，跟手动录入完全同一条链路）；
识别**同步**等结果（5~15 秒，用户盯着转圈），不走队列 —— 一天就那么几次，不值得为它常驻 worker。

## 二、接口

| 接口 | 说明 |
| --- | --- |
| `GET /api/items/recognize/status` | `{enabled, leftToday, dailyLimit, maxItems}`（免登录？**要 token**） |
| `POST /api/items/recognize` | multipart `file=<穿搭照>` → 识别结果；`throttle:10,1` |

业务码（接在洗白底 4010 后面，**不复用 4009/4010**，免得前端分不清是哪件事的次数用完）：

| 码 | 含义 |
| --- | --- |
| 4020 | 识别功能没开（服务端开关） |
| 4021 | 今天识别的次数用完了 |
| 4022 | 照片有问题（读不到 / 不是图片） |
| 4023 | 一件都没认出来（换张全身清楚的正面照） |
| 4024 | 识别失败（供应商侧 / 上传失败） |

## 三、线上要配的 env

```
SCAN_ENABLED=false          # 总开关；先发代码不生效，确认能跑了再改 true
SCAN_MODEL=qwen-vl-plus     # 认不准就换 qwen-vl-max（贵一些）；改这里不用发版
SCAN_DAILY_LIMIT=5          # 每人每天几次（调用失败会回滚，不吃用户次数）
SCAN_MAX_ITEMS=8            # 一次最多认几件（防一张图占掉一堆衣架）
SCAN_CROP=true              # 按框裁图当衣物照片；false = 认出来的先没照片
SCAN_CROP_PADDING=0.06      # 裁剪四周留的余量
SCAN_CROP_MAX_SIDE=900      # 裁剪图最长边
SCAN_TIMEOUT=90             # 单次调用超时（秒）
```

用的是**同一把** `DASHSCOPE_API_KEY`（跟 AI 试穿 / 洗白底共用），不用新申请。

## 五、实测踩到的坑（别改回去）

1. **模型给的框是「绝对像素」，不是 0-1000 归一化**。提示词里只写「0-1000 归一化」时，
   `qwen-vl-plus` 会给出 `[305,1228,471,1312]`（图高只有 1344）—— 按 1000 去换算就是越界，
   鞋/裤子那几件会被当成坏框丢掉。现在两头都认（`ScanService::boxToPixels`）：
   坐标 > 图片长边、或全都 ≤1000 而图比 1000 大 → 按 0-1000 算；否则按绝对像素。
   **提示词里也写明了「图宽 {w} 像素、高 {h} 像素」**（运行时把真实尺寸填进去）。
2. **百炼只吃公网 https 直链**。本地盘驱动（没配 OSS）时给的是 `域名/storage/...`，会被数据检查拒
   （报 `InvalidParameter.DataInspection`）。跟洗白底是同一个坑。
3. **一双鞋会输出两条**（左右各一条）。提示词里加了「成对的合成一条」后实测从 4 条变 3 条。
4. **PHP 常量表达式不能调用函数**：`private const CATEGORIES = array_keys(self::SUBS)` 直接
   `FatalError: Constant expression contains invalid operations`。改成 `isset(self::SUBS[$cat])` 判断。
5. **`Cache::increment` 一个不存在的键会建一条永不过期的记录**（database 驱动）→ 次数跨天不清零。
   必须先 `Cache::put($key, 0, 今天结束)` 再 increment。
6. **裁剪阈值别卡太紧**：一开始要求「面积 ≥ 整图 1%」把鞋（1.3% 上下浮动）全丢了。
   现在是 0.4% + 最短边 20px，同时拒绝占满整图（>92%）的框。

## 六、花费 / 已知取舍

- 花钱的地方：① 每次识别一次 `qwen-vl` 调用（几分钱）② 每张图的原图 + 裁剪图存 OSS（都很小）
- **每次识别会在 OSS 留一张原图**（`scan/{uid}/...`）+ N 张裁剪图。裁剪图是衣物照片，原图目前**没有清理逻辑**
  （留着是为了以后支持「重裁 / 拖框微调」）。要清的话单独做，不自动删。
- 识别失败（调用/解析错）会**回滚次数**；「调用成功但一件没认出来」**照样计次**（调用确实发生了）。
- 裁剪质量：裤子/上衣这类大件的框挺准；鞋、包这种小件是特写（不糊，但也没什么构图）。
  框偏了用户可以点「换成整张穿搭照」，或者干脆不带照片入库。

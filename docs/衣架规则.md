# 衣架规则（2026-09）

> 客服照着这份回答"为什么我的衣架少了 / 怎么加"。规则改了口径要同步改这里 + `pages/hanger` 说明页。

## 一、概念

一个衣架挂一样东西：**录一件衣物占 1 个，存一套搭配也占 1 个**，衣物和搭配共用一个架子。
为什么有上限：衣物照片存在云端（OSS）有成本，所以免费能挂的数量有限。

| 数字 | 默认 | 说明 |
| --- | --- | --- |
| 总共衣架 | 100 | **建号时送一次，之后不再送**；用户的"资产"，删掉东西会还回来；签到/分享/每月免费领取会加；客服也能加 |
| 总共衣架上限 | 200 | 奖励（签到/分享/每月领取）加到这么多就**不再累加**；客服手改和老账号不受限 |
| 今日衣架 | 100 | 每天 00:05 重置回 100；用不完不累积 |

数字存在 `users.item_quota`（总共余额）/ `users.daily_quota`（今日余额），
后台 Filament → 用户 → 「衣架余额（总）/（今天）」，**给用户加衣架就改这两个数**。
免费标准（新用户送多少 / 每天多少）在 `config/quota.php`，`.env` 的 `QUOTA_*` 可覆盖，
改数字**不用发小程序版本**（数字全部由接口下发，前端一个都不写死）。

**界面上那两个数字**（「我的」页衣架卡显示「衣架 97 / 100」，说明页写「还剩 / 总共」）：

| 位置 | 是什么 | 什么时候变 |
| --- | --- | --- |
| 左边 | `item_quota`（还剩几个，能马上用的） | 新增 -1、删掉 +1、赚到 +N、客服加 +N |
| 右边 | **余额 + 已占用**（衣物数 + 搭配数）= 这个账号一共有多少衣架 | 只有赚到（签到/分享/每月领取）和客服加量才变大 |

右边这个分母 2026-09 改过一次（用户）：老口径是 `max(免费标准, 余额)`，
余额一超过免费标准（比如领了奖励变成 162）分母就等于余额，界面显示「162 / 162」，
加一件衣物变「161 / 161」—— **两个数一起减，看着像没有上限**。
现在改成"余额 + 已占用"（`Quota::occupied()`）：加一件衣物余额 -1、占用 +1 → 分母不动，
显示「161 / 162」。账是平的：`余额 + 已占用 = 这个账号总共拿到过的衣架`。

## 二、什么时候占衣架（`ClothesController::billable`）

**原则：衣架 = 云端挂着的一样东西。只有净增长才占，净减少就还 —— 编辑类操作不占。**

| 操作 | 占几个 | 为什么 |
| --- | --- | --- |
| 录一件新衣物 | 1 | 云端多了一张照片 |
| 存一套新搭配 | 1 | 云端多了一张封面图 |
| 搭配里**换了衣物** | 0 | 只改字段，没有任何上传 |
| **重新出封面** | 0 | 是"换一张"：新图传上去，旧图由 `deleteByUrl` 删掉，总数没变 |
| 给衣物**换照片** | 0 | 同上，旧的会被删 |
| 只改名字 / 场合 / 颜色标签 | 0 | 纯元数据 |
| 后台把内容原样再推一遍（同步/补传） | 0 | 内容没变 |
| 删掉衣物 / 搭配 | **−1（还）** | 云端少了一张图 |

账是平的：`余额 = 上限 − 云端现在挂着的（衣物 + 搭配）数量`。

## 二之二、赚衣架：每日签到 / 分享群或好友 / 新用户每月免费领取（2026-09）

「我的」页衣架卡右侧的「获取更多」进的是 `pages/reward`，三件事真能加衣架（都要点）：

| 动作 | 加几个 | 频率 | 说明 |
| --- | --- | --- | --- |
| 每日签到 | +1 | 每天 1 次 | 按日期算，昨天领过今天照样能领 |
| 分享群或者好友 | +2 | 每天 1 次 | 点一下转发按钮就算（见下面「为什么」） |
| 新用户每月免费领取 | +50 | 每自然月 1 次 | **要点一下「领取」才到账**；这个月没点就没了（不补发、不累计），下个月按钮又变回「领取」 |

- 奖励**加到总额**（`users.item_quota`），**今日额度不动** —— 赚来的是资产，不是当天速率
- 奖励**受衣架总数上限约束**（`config('quota.item_max')`，**200 个**，2026-09 用户定）：
  加到 200 就不再累加，少给的部分直接丢（不存着等下次）。
  这时的提示语是「衣架已经到上限 200 个了，这次的先不累加」，**不会报一个用户看不到的 +N**；
  快满时只加装得下的那部分（余额 199 + 签到 2 → 只加 1，提示语就说 +1）。
  上限只拦奖励：客服在后台手改余额、老账号早就超过 200 的，都不受影响；
  **删掉东西退还的衣架也不受它管**（那是把用户自己用掉的还回来，不是白赚）
- 免费额度（`item_quota`，100）只是"免费进货量"，**不是天花板** —— 真正封顶的是上面这个 200
- 数字（+1 / +2 / +50 / 每天几次）全在 `config/quota.php` 的 `reward_*`，改数字不发版；
  把某个数字设成 0 就等于关掉这个奖励（签到/分享会回 4009，每月领取那一行则不显示）
- **"每月免费领取"原来是"每月系统赠送"**（2026-09 用户改的口径）：老口径是**自动到账** ——
  用户一打开「我的」页就惰性补发，流水记在本月 1 号。现在改成**用户点一下才给**，
  流水记在**领取当天**（type=`newcomer`），按月去重还是靠"同一自然月只算一次"。
  老口径的代码和配置都留着（`reward_monthly`，默认 0 = 关闭），要退回自动发就把它设 >0。
- 防重复：`hanger_rewards` 表上 `unique(user_id, type, reward_date, seq)` + 事务里锁用户行，
  连点两下也只领到一次（第二次回 4008）
- **为什么分享是"点一下就算"**：微信从 2021 年起不再返回"是否真的转发成功"，
  小程序拿不到结果，只能按"点了分享按钮"发奖励。单次 2 个，最坏情况是有人点开面板又退出白拿一次，
  成本可接受（用户 2026-09 定）；要严一点就得改成"好友从卡片点进来才算"，那需要带邀请参数 + 好友首访去重。
- **分享按钮的样式固定**（2026-09 用户定）：今天已经领过奖励也不灰、文字也不换成"明天再来"，
  就是实心主题色「分享群或者好友」（分享本身就值得鼓励）；领没领过写在按钮上面那行小字里。
  签到按钮保持原样（领过 → 灰掉 +「明天再来」）。

## 三、删除会还，但只还总额

- 删掉一件衣物或一套搭配 → **总共衣架 +1**（回到架子上）
- **今日衣架不回补** —— 今日是"今天最多挂 100 个"的速率限制；
  如果也回补，「加满 100 → 全删 → 再加满」就能无限循环，限制形同虚设
- 不会越还越多：只有"这次真的从没删变成已删"才还 1 个（重复推已删的 id 不再还）
- 衣架不够被拦时**整批回滚**：这次的写入和这次要还的衣架一起回滚，不留半截状态

## 四、不够了怎么拦

| 业务码沿用：**4001 = 总衣架不够**、**4002 = 今日衣架不够**（奖励那边是 4008 今天领过了 / 4009 奖励没开）
- 后端 `App\Services\Quota::consume()` 负责拦，文案就在那里（前端直接显示后端的 msg）
- 前端**四处**都接了这个码/口径：
  1. 录入衣物（item-edit）
  2. **录入前的预检**（wardrobe 的「＋」）
  3. **新建搭配的预检**（outfit 的「＋」）—— 2026-09 用户要求：衣架没了就在这个入口拦下，
     别让人挑完一套衣服点「完成」才被后端拦（口径跟 wardrobe 那个预检完全一致：
     标题分「今天挂满了 / 衣架用完了」，主按钮联系客服）
  4. 存搭配（outfit-view 的「完成」）
- 用完时的出路：**删掉不想要的腾出衣架**，或**联系客服**

## 五、口径改过的历史（别改回去）

1. 最初只限衣物，穿搭完全不限 → 2026-09 起穿搭也占
2. 编辑到底占不占，来回定过一次：一度改成"改了内容就占"，**当天又改回"不占"** ——
   因为换封面/换照片都是"换一张"，旧图会被 `deleteByUrl` 删掉，云端总数没变、成本没涨。
   结论：只有净增长（新增）才占。**别再改回去了**，除非哪天不再删旧图。
3. 最初"删除不还" → 2026-09 起**删掉会还总额**（今日不还）
4. 免费额度来回定过几次：200/50 → 500/200 → **50/100**（2026-09 定稿）→ **100/100**（2026-09 用户再改）。
   数字只影响**新用户**（建号时按配置写一次）；老用户余额不动，要补得单独写迁移（见下）
5. 加了"赚衣架"：签到、分享（奖励只加总额）
6. 加"每月系统赠送 +50"（2026-09）：按自然月、惰性补发，记在本月 1 号
7. **免费额度只送一次**（2026-09 用户确认）：`users.item_quota` 只在 `UserController::login` 建号时按
   `config('quota.item_quota')` 写一次；之后能变的只有"删除退还 / 赚衣架 / 客服后台加"。
   没有"每次登录送"这种逻辑
8. **"每月系统赠送"改成"新用户每月免费领取"**（2026-09 用户改）：周期不变（每自然月 1 次），
   但从"系统自动到账"改成"**用户点一下「领取」**"（`POST /api/hanger/newcomer`，流水 type=`newcomer`）。
   这个月没点就没了 —— 不补发、不累计。
   老口径的代码（`HangerRewardService::grantMonthly`）和配置（`reward_monthly`，默认 0 = 关闭）都留着，
   想退回"自动送"把它设 >0 即可，不用改代码。
9. **分享文案改成「分享群或者好友」**（2026-09 用户改）：
   `pages/reward` 那一行的行名和按钮文字都改了；
   顺带把分享按钮的样式**固定**成"可点"的样子（领过了也不灰、文字不变）。
9.1 **奖励数字调小**（2026-09 用户改）：签到 2 → **1**、分享 10 → 4 → **2**（`reward_checkin` / `reward_share`）。
10. **衣架总数上限 200**（2026-09 用户定）：`config('quota.item_max')`，
    奖励（签到/分享/每月领取）加到 200 就不再累加；`Quota::addTotal()` 返回**实际加到的数**，
    提示语用它拼（到顶就说"已到上限"，快满就报实际那几个）。上限不管客服手改和"删掉退还"。
11. **衣架说明页隐藏**（2026-09 用户定）：「我的」页衣架卡**点哪儿都进「赚衣架」页**
    （中途放出来过一次，用户觉得说明页内容写得不合适，又收回隐藏）。
    页面文件、app.json 注册都留着；要放出来就把 `pages/mine/mine.js` 的 `onHanger()` 指回 `/pages/hanger/hanger`。
